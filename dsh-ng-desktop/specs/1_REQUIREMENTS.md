# 产品需求定义

## 1. 产品定位

**dsh-ng-desktop** 是 DeepSeek Harness（DSH）的第三方跨平台桌面客户端，主要面向 Windows，同时支持 macOS。客户端负责 DSH 的安装、启动、停止、托盘驻留、自启动注册和干净卸载；DSH 的业务界面直接使用其原生 Web UI。

客户端不修改 DSH Web UI，不承担 DSH 或客户端的版本比较、更新提示和兼容性管理。

## 2. 发行与安装

### 2.1 正式发行形态

- 项目受支持的发行目标只有 Windows `win-x64` 和 macOS `osx-arm64`；两者共享安装流程与桌面运行逻辑。Windows ARM64、macOS Intel 及其他架构仅允许用户从源码自行构建，不生成、发布或验收对应发行物。
- Windows 正式下载物是唯一的 `DshDesktopSetup.exe` 单文件入口。它只承担无界面的负载校验、解压、进程等待和临时目录清理；安装过程中唯一可见的产品界面是 Avalonia 原生安装引导，不叠加第二套安装向导。
- macOS 正式下载物是当前用户安装的 `pkg`；其安装后脚本只启动同一 Avalonia 安装事务，将客户端部署到用户的 `~/Applications/DSH Desktop.app`，不另行实现第二套安装向导。
- 正式安装包只通过项目 GitHub Releases 发布，由用户手动下载和安装；不规划 Microsoft Store、WinGet 或客户端内更新渠道。
- GitHub Release 必须提供版本化产物、SHA-256、系统与 Node 前置条件和签名状态；已发布的同名版本文件不得替换。Windows 和 macOS 当前均允许发布明确标记为“未签名社区预览”的安装包：Windows Release 必须说明 SmartScreen 风险，macOS Release 必须说明 Gatekeeper 警告或拦截风险、一次性人工打开要求及 SHA-256 校验步骤；不得要求用户导入根证书或发布者证书，也不得指导用户全局关闭系统安全保护。
- 本仓库的每个可发行子项目独立维护版本和 GitHub Release；桌面客户端的 Release 标签固定为 `desktop-v<SemVer>`，例如 `desktop-v0.9.1`，不得使用会与插件或其他子项目冲突的仓库级裸版本标签。
- `dsh-ng-desktop/CHANGELOG.md` 是发行更新说明的唯一来源。维护者自主选择 SemVer 的 major、minor 或 patch，并在推送标签前将同版本条目及精炼的用户可见更新写入 Changelog；CI 不根据提交自动推断、修改或提交版本号。标签必须指向包含同版本 Changelog 条目的提交。
- 维护者必须在推送发行标签前，于真实 Windows `win-x64` 和 macOS `osx-arm64` 环境分别完成人在环安装、运行和卸载验收。推送 `desktop-v<SemVer>` 标签后，GitHub Actions 分别在干净的 Windows 与 macOS Runner 上重建支持的安装包和 SHA-256；仅当全部构建成功时，发布任务才创建同名 GitHub Release、上传附件，并写入对应 Changelog 条目、上一个桌面标签以来的提交数量与比较链接。Release 不逐条罗列每次提交或自动生成详细提交日志。
- 当前自动发布只生成明确标记的未签名社区预览，不向 GitHub Actions 提供签名私钥、Apple ID 或公证凭据。未来启用正式代码签名或公证时，必须改为受控签名环境或经过审批的签名任务，不能把长期签名凭据交给普通 CI Runner。
- 本地构建安装包及校验值只写入 `dsh-ng-desktop/artifacts/installer/`，该目录属于本地发行物，绝不进入 Git 源码。
- macOS `osx-arm64` 包不签名、不公证、不使用自签名或 ad-hoc 身份；Release 必须如实提示 Gatekeeper 风险。GitHub Actions 只使用 macOS Runner 自带的系统打包工具，不保存任何 Apple 凭据。
- 正式发行不以“解压即用”或单个便携程序替代安装器，因为便携模式无法完整保证事务回滚、系统卸载、自启动注册和残留清理。

### 2.2 构建形态

- 每个 Windows `win-x64` 发布版本必须同时提供两种安装器：Native AOT 自包含客户端包和 .NET 依赖客户端包；两者使用相同安装事务、产品 ID 和卸载逻辑，但文件名必须明确标识已安装客户端的构建形态。每个 macOS `osx-arm64` 发布版本只提供 Native AOT、自包含 `pkg`，复用同一产品状态机、产品 ID 和卸载逻辑。
- Windows `SetupHost` 始终使用不依赖 Avalonia 的 Native AOT、自包含 `WinExe`，保证两种安装包都能在没有命令行窗口的情况下完成负载准备并显示明确的引导失败信息。
- Native AOT 包中的桌面客户端及全部 .NET 辅助程序自包含构建，目标机器无需安装 .NET。
- .NET 依赖包安装框架依赖桌面客户端，目标机器必须预先安装匹配主版本的 .NET Desktop Runtime；`SetupHost` 在启动 Avalonia 负载前检测此前置条件。该要求必须出现在 GitHub Release 和安装包文件名中。
- Native AOT 是代码设计和正式发布的硬性准入条件，不得先编写依赖 JIT、动态代码生成或未声明反射的实现，再以非 AOT 产物绕过。
- .NET 依赖包用于已有 .NET 运行时的环境，以减小下载体积；它不是 AOT 正式准入的替代品。
- 支持开发者安装 .NET SDK 后直接从源码执行普通构建，并以显式 `--development` 参数运行开发宿主；未带参数的 `DshNgDesktop.exe` 只代表已安装客户端，不根据执行位置猜测安装角色。
- Windows 正式构建和发布固定为 `win-x64`，macOS 固定为 `osx-arm64`；不维护 Windows ARM64、macOS Intel 或其他 RID 的项目构建、发布和验收矩阵。
- 每个安装负载必须携带客户端 SemVer 和构建形态（`AOT` 或 `.NET 依赖`）元数据；安装清单保存该元数据，供后续安装器在本地识别升级、同版修复、降级和构建形态切换。旧版缺少元数据时必须以未知版本兼容处理，不得阻断安全的保留数据安装。

### 2.3 安装事务

- DSH 是客户端安装事务的一部分，不得等客户端安装完成后再以“首次启动任务”补装。
- Windows 安装器使用唯一的中文 Avalonia 原生安装引导窗口展示环境检测、阶段进度、日志摘要、失败原因和停止操作，并可打开安装位置；目标尚未创建时只打开其现有父目录，不为查看位置创建安装目录。`SetupHost` 不显示安装向导，只允许在负载无法校验、解压或启动时显示操作系统原生错误对话框。
- 安装窗口打开时对旧安装清单、版本和构建形态的读取不得同步阻塞 Avalonia UI 线程；检测期间窗口保持可重绘和可关闭，读取失败进入可见错误状态，不得出现只能结束进程的不可操作窗口。
- 单文件 `SetupHost` 必须内嵌一份完整客户端发布负载，将其安全解压到本次运行独占的临时目录，再以显式安装参数启动其中的客户端并同步等待整个安装引导进程退出。禁止经过 IExpress、`cmd.exe`、PowerShell 或其他会提前返回的脚本启动链。
- 临时负载中的全部路径必须经过规范化和目录边界验证；拒绝绝对路径、父目录穿越、符号链接和其他重解析点。`SetupHost` 只有在安装引导进程退出后才可删除临时目录，不得删除仍被引导程序使用的文件。
- 单文件安装器必须包含 Avalonia 引导启动所需的全部托管和原生运行库；不得假定发布目录中的主 `.exe` 可以脱离其同级原生库独立运行。发布负载不得包含 PDB、构建缓存或其他调试产物。
- 引导程序显示“安装完成”后，用户关闭窗口，`SetupHost` 才清理临时负载并启动已安装的客户端；失败或停止时等待回滚结果可见，用户关闭失败页后再清理临时负载并以非零退出码结束。
- `DshNgDesktop.exe` 的无参数入口只表示已安装桌面客户端；安装事务只能通过 `SetupHost` 传入的显式安装会话参数启动，不再根据当前执行目录或安装清单缺失隐式猜测自身角色。
- 安装成功必须同时满足：客户端文件就位、DSH 进程成功启动、本地 Web UI 健康检查通过、自启动、系统卸载入口和 Windows 当前用户桌面/开始菜单快捷方式完成注册。
- 任一阶段失败或用户停止时，安装事务失败；安装器必须停止受管进程、清理本次创建的数据、取消系统注册并回滚客户端文件。
- 失败信息在回滚前保持可见，允许用户复制或打开安装日志。
- 若检测到旧产品数据，安装器必须先要求用户选择：覆盖安装仅替换客户端文件并保留 DSH 数据；全新安装在明确确认后清理全部产品受管路径再安装。当前安装日志在安装器退出前保留供诊断，不因全新安装被删除。有效安装清单证明该范围属于产品，仍可供用户选择两种方式；无清单的中断数据也可选择两种方式。无法验证的清单状态只允许用户明确选择全新安装，不得自动清理或扩大删除范围。
- 保留数据的安装替换已完成安装的客户端前，必须通过单实例 IPC 请求运行中的客户端进入维护停止状态；运行中的客户端先销毁 WebView、优雅停止其受管 DSH 并退出，安装器取得维护锁后才能替换安装目录。IPC 未确认、旧实例未退出或维护锁超时，安装必须显示明确失败原因并保留原安装，不得卡死、强制结束无关进程或直接删除仍被使用的文件。
- 版本识别只在本地安装器内进行：新版本显示“升级安装（保留数据）”，同版本显示“修复/重新安装（保留数据）”，较旧版本显示“降级安装（保留数据）”及警告，跨 AOT/.NET 依赖切换显示构建形态变化；不联网查询 GitHub、不自动下载客户端更新。
- 全新安装清理产品私有目录时，必须能处理依赖缓存留下的只读项，不跟随符号链接或其他重解析点；清理仍失败时必须保留未删除内容，并明确指出受管根目录和失败项，而不是只显示无上下文的子目录名称。

### 2.4 Node.js 前置条件

- 客户端不携带、不自动安装、不卸载私有 Node.js。
- 安装器必须先检测系统已有的 `node` 与 `npx`，并验证其能够启动 DSH。
- 首次 `npx` 供应 DSH 时，安装器必须持续等待至 DSH 就绪、受管进程退出或用户停止；不得以普通启动的短超时或固定安装时限中止首次安装。
- 长时间供应期间，安装器必须以单一主状态、单一已等待时长和有意义的摘要进展展示过程；在长时间无新输出时提示仍在等待且可随时停止，不将其直接报告为安装失败。
- Node.js 缺失或不兼容时，安装立即停止并提供明确的安装指引；用户修复环境后重新运行安装器。
- 卸载不得删除用户或其他软件安装的 Node.js、npm 配置和共享 npm 缓存。

## 3. DSH 管理

### 3.1 安装与启动命令

- DSH 必须通过未锁版本的 `npx @deepseek-ai/dsh web` 安装并运行，禁止改用 `npm install`、全局 npm 安装或客户端自维护包更新。
- 客户端允许 npx 在后续启动时取得变化后的 DSH 版本，不比较版本、不提示可用更新、不回滚 DSH 更新；启动过程可如实显示“正在检查 DSH 更新”，并仅在 npx 输出表明正在下载、解压或安装包时显示“正在更新 DSH”，不显示具体版本或伪造百分比。
- 启动状态必须明确区分启动失败、DSH 运行中异常退出、检查 DSH 更新时的网络错误和更新 DSH 失败；主窗口与后台托盘显示同一错误类别及简短说明，完整 npx 输出只写入运行日志。
- npx 执行缓存必须定向到客户端私有目录，避免污染或依赖用户的共享 npm 缓存。
- `DSH_HOME` 必须定向到客户端私有目录，使 DSH profile、配置、凭据、插件和会话具有明确的卸载归属。
- DSH 从客户端专属的空白启动目录运行，不把客户端安装目录或任意用户目录隐式设为工作区。

### 3.2 进程与端口

- 客户端只管理自己创建的 npx、Node 和 DSH 进程树，禁止按进程名称批量终止系统中的 Node 进程。
- DSH 仅监听 loopback。默认优先使用 3080；端口被未知进程占用时选择并持久化其他可用端口。
- 安装和正常启动均以 DSH Web UI 健康检查通过作为就绪条件，不以端口可连接或进程仍存活作为唯一依据。
- 正常停止先请求 DSH 优雅退出，超时后再强制终止客户端拥有的进程树。
- DSH 异常退出时，客户端显示故障状态和日志入口，不进行无上限自动重启。
- 客户端提供共享的环境诊断能力，供安装器、故障页面和可选命令行诊断复用；诊断默认只读。
- 自动修复仅限安全操作：重新定位 Node/npx、重试启动，以及确认私有 npx 缓存损坏后清理该缓存并重试一次。
- 自动修复不得删除 `DSH_HOME`、修改系统 Node/npm 环境或无限循环重试。

### 3.3 本地测试工程

- 单元测试工程固定放在 `dsh-ng-desktop/LocalTests/`，仅供本机开发与验收使用，不进入 Git 协同。
- 本地测试工程可以引用桌面项目，并只可创建其自身临时目录及测试专属产品数据根目录；不得把测试产物写入安装目录、用户共享 npm 缓存、真实 `DSH_HOME` 或用户工作区。
- 正式代码必须保持可自动化测试的窄接口边界；本地测试工程的存在、缺失或内容均不得影响应用构建、打包、安装器或正式发行物。

## 4. 桌面体验

### 4.1 原生窗口与 WebView

- 客户端使用 Avalonia 标准桌面生命周期和操作系统原生标题栏。
- 环境检测、安装进度、回滚和运行故障页面全部使用客户端原生 Avalonia UI。
- 只有 DSH Web UI 使用内嵌 `NativeWebView`；在 DSH 健康检查通过前不得创建或显示业务 WebView。
- WebView 直接呈现 DSH Web UI，不添加客户端导航限制，不拦截外部链接，不提供网页到宿主的脚本桥接。
- Windows 使用客户端私有 WebView2 用户数据目录；macOS 使用独立的 WKWebView 数据存储标识。相关缓存随客户端卸载。
- 已安装客户端关闭主窗口时，必须销毁当前业务 WebView 并允许 WebView2 子进程退出，同时保留托盘、客户端宿主与 DSH 服务；用户从托盘重新打开主窗口时，按已就绪的 Web UI 地址重新创建 WebView。
- 客户端记录安装与运行日志，并提供可理解的错误摘要和日志位置。
- 安装引导的日志面板展示经整理的摘要而非完整依赖下载输出，支持自动换行、紧凑行距、手动滚动、文本选择和复制；用户查看历史内容或选择文本时，后续日志不得强制跳回末尾或清除选择。

### 4.2 托盘与窗口生命周期

- 托盘统一使用 Avalonia `TrayIcon` 和原生菜单能力，不自行实现 Win32 托盘。
- Windows 左键托盘图标打开主窗口，右键菜单至少提供“打开 DSH”和“退出”。
- macOS 遵循菜单栏图标的原生交互，在菜单中提供“打开 DSH”和“退出”，不强求复制 Windows 左右键行为。
- 后台自启动时不显示主窗口；托盘提示文本应反映 DSH 的启动阶段、就绪或失败。用户从托盘打开主窗口后，看到与前台启动一致的原生状态。
- 安装完成后的窗口关闭操作隐藏主窗口并保留托盘和 DSH；安装事务中的关闭操作等同于停止并回滚前的确认。用户已确认停止后，`Stopping` 和 `RollingBack` 为不可中断阶段：再次关闭窗口必须被拦截，窗口保持显示“正在停止/回滚”，直至终态结果可见，不能提前退出而留下未清理目录。
- 托盘“退出”必须先停止 DSH，再退出客户端。
- 客户端只允许运行一个实例；重复启动时激活既有实例的主窗口。

## 5. 开机自启动

- 安装事务成功时默认注册当前用户开机自启动，自启动参数以后台模式启动客户端和 DSH，不主动弹出主窗口。
- Windows 安装事务同时为当前用户创建“DSH Desktop”开始菜单和桌面快捷方式；快捷方式直接启动受管安装目录中的客户端，不依赖下载的安装器或临时目录。
- 客户端内不提供自启动开关；用户通过操作系统设置启用或禁用。
- 客户端启动和升级不得重新启用已被用户在操作系统中禁用的自启动项。
- 卸载必须注销本产品的自启动项，不影响其他登录项。

## 6. 干净卸载

卸载必须：

1. 卸载器通过客户端单实例 IPC 通知运行中的客户端进入卸载状态并停止接受新操作；收到确认后等待该实例完全退出，未确认或未退出时不得开始文件删除。
2. 销毁 WebView，优雅停止 DSH，必要时强制终止客户端拥有的进程树。
3. 注销 Windows 或 macOS 自启动项及产品安装注册。
4. 删除 Windows 当前用户桌面和开始菜单快捷方式。
5. 删除客户端安装目录、状态、日志、私有 npx 缓存、`DSH_HOME`、WebView 数据和安装中间目录。
6. 删除客户端安装的 DSH profile、插件、会话、配置和凭据。
7. 保留用户选择的所有工作区目录及其中的全部文件，不尝试回滚 DSH 曾对工作区执行的修改。
8. 保留系统 Node.js、用户 npm 配置、共享 npm 缓存和非本客户端创建的进程。

Windows 与 macOS `osx-arm64` 均通过其受管安装入口执行完整清理；其他平台兼容性代码不构成项目发行或清理验收承诺。

## 7. 非目标

- 客户端运行期和 DSH 的联网版本比较、更新下载、版本固定和兼容性治理。
- 修改、复制或替代 DSH Web UI。
- 远程 DSH 连接。
- 客户端内的自启动开关。
- Linux 正式发行。
- Windows ARM64、macOS Intel 和其他未列出的处理器架构的安装包、CI 构建与发行验收。
- 当前版本的 macOS 签名、公证或要求用户导入证书的发行路径。
- 删除或恢复用户工作区内容。
- Microsoft Store、WinGet 和其他应用商店发行。
- 客户端内下载或安装客户端更新。
