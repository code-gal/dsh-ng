# 交付与验收规范 (Verification Criteria)

本规范用于界定 `dsh-ng-desktop` 相关的模块必须满足怎样的表面特征或黑盒表现，才被允许在 `3_TASKS.md` 中标记为 "已完成 (Done)"。这也作为后续进行人肉 QA 及未来 CI 自动化的锚点。

## 里程碑 1 测试锚点 (底座搭建)
- **T1.1**: 执行 `dotnet run` 能够弹出一个无样板（没有任何无关第三方 UI）的原生托盘。
- **T1.2**: 托盘具有正常的原生右键菜单，能够直接点击出空转响应。
- **T1.3**: 再次启动应用时，不产生新的 `.json` 文件乱改端口配置，能够正确复读取已固定的本地随机可用端口号。

## 里程碑 2 测试锚点 (派发流程)
- **T2.1 (离线断言)**: 若本机未装 npm，启动应用应该弹出醒目失败错误而不是进程闪退。
- **T2.2 (路径干净断言)**: 一次干净运行后，检查 `%LocalAppData%` (全局) 域。只有自己的专属私有目录下应当出现 `node_modules` 和 dsh 的依赖，系统原生全局 `%AppData%/npm/node_modules` 不受任何该进程安装所带来的影响。
- **T2.3 (运行断言)**: 使用托盘“打开面板”能够成功弹起默认浏览器，并渲染 dsh 的原生界面。控制台里没有弹出的黑色执行窗框（静默达标）。
- **T2.4 (自启断言)**: “开机启动”能够精准在 Win11/10 的任务管理器启动项列表里勾勒可见目标。
- **T2.5 (首次安装可见)**: 干净数据目录下首次启动必须弹出“是否现在安装”确认框；确认后立刻出现“正在安装”提示，完成或失败都有对话框，不能只有托盘无反馈。
- **T2.6 (面板入口门禁)**: 未安装时右键菜单没有“打开面板”；安装完成后该入口才出现。点击打开面板不得再触发安装。
- **T2.7 (手动更新)**: 已安装启动时可提示有新版本，但不会自动改写本地包。菜单“检测更新”给出明确结果；只有用户确认“更新”后才执行 npm 升级。

## 里程碑 3 测试锚点 (极致的自焚体验)
- **T3.1**: 选择完全彻底卸载后，检测到后台所有关联包含字眼 `node` 或指派自此层的派生进程全部挂掉。
- **T3.2**: 托盘消失。
- **T3.3**: 此时进入回收目录，原本的 `%LocalAppData%/dsh-ng-desktop` 以及里面的上百 MB 的 dsh 相关包全部消失不见。
- **T3.4 (幽灵断言)**: 去看被引开释放出来的独立临时卸载 `.bat`。2秒后不仅 `.exe` 层消失，`.bat` 也随之自己清除，未留下任何蛛丝马迹。

## 里程碑 4 测试锚点 (安装向导窗口)
- **T4.1**: 未安装时启动应用直接显示安装向导窗口，而不是只有托盘菜单。
- **T4.2**: 安装过程中能看到阶段状态、日志滚动和失败原因。
- **T4.3**: 安装成功后自动启动 DSH，并打开浏览器到本地面板地址。
- **T4.4**: 关闭向导窗口不会退出后台托盘。

## 综合测试策略
除了上述基于表现层的场景锚点外，整个工程的测试方法论需包含：

### 1. 自动化单元测试 (Unit Testing)
- **本地化与防污染 (Git Ignore)**：单元测试代码被视为私有辅助资产，**不得进入 Git 仓库提交**。所有的单元测试工程命名均放置在 `LocalTests/` 文件夹下或以 `.LocalTests` 结尾（已在根目录 `.gitignore` 配置）。确保其不会污染生产代码架构与 CI 流程。
- **核心逻辑必测**：对于纯业务性的领域逻辑（如 `Configuration.cs` 的随机端口可用性算法、文件路径安全拼接等），必须在隔离的本地单测工程中实施高覆盖率单元测试。
- **边界解耦**：当模块与系统底层（托盘 API、Windows 注册表等）耦合度高时，不必编写脆弱的自动化集成测试，优先将核心逻辑从外部依赖中剥离抽象。

### 2. 人在环验收测试 (Human-in-the-Loop, HITL)
鉴于该桌面程序具有极强的操作系统和 GUI 交互绑定性，无法也不应全依靠自动化脚本：
- **真实体感测试**：托盘唤起时的顺滑度、自动拉起浏览器的时间延迟、退出与卸载清理残留的最终检视，都必须依赖开发人员/QA 在真实的 Windows 机器里亲自点按来确认表现。
- **黑盒准出兜底**：前文定义的「里程碑测试锚点」均默认并强烈推荐由人在环（HITL）的形式亲自验证闭环把关。
