# 交付与验收规范

只有满足对应验收项，`3_TASKS.md` 中的任务才允许标记完成。

## 1. 工程基线

- **V1.1**：普通 `dotnet build` 成功，启动骨架不执行旧托盘、旧安装、更新或 WebView 实验逻辑。
- **V1.2**：生产代码中不存在 Win32 托盘实现、`npm install @deepseek-ai/dsh`、更新检测、自定义标题栏和 WebView 导航白名单。
- **V1.3**：Windows 与 macOS 平台能力通过窄接口隔离，共享状态机不散布平台判断。
- **V1.4 AOT 静态门禁**：AOT、Trim 和 Single-file 分析器持续启用，生产项目不存在未处理的相关警告。
- **V1.5 AOT 编码约束**：生产代码不使用运行时程序集加载、`Reflection.Emit`、动态代理、反射扫描式注册或运行时代码编译；JSON 和平台调用采用规定的 Source Generator。

## 2. 安装事务

- **V2.1 环境缺失**：Node 或 npx 缺失、不兼容时，安装器显示明确原因和修复指引，退出为安装失败。
- **V2.2 原生界面**：环境检测、阶段进度、日志摘要、停止和失败页面均由 Avalonia 原生 UI 呈现，不创建业务 WebView。
- **V2.3 成功提交**：只有客户端文件就位、DSH 启动、Web UI 身份验证通过和自启动注册成功后，安装器才报告成功。
- **V2.4 用户停止**：任一未提交阶段点击停止，受管进程树退出，客户端文件、私有缓存、系统注册和中间目录完成回滚。
- **V2.5 失败回滚**：模拟下载失败、进程异常退出、端口竞态、健康检查超时和自启动注册失败，均不留下可运行的半安装客户端。
- **V2.6 日志可用**：失败结果保持可见并允许打开日志位置或复制诊断信息；日志不含 API Key、令牌和完整敏感环境变量。
- **V2.7 长等待与摘要交互**：模拟首次供应超过普通启动时限时，安装器持续等待且显示阶段、已等待时长及可读摘要，不自动退出；停止可取消等待并回滚。日志面板自动换行、可手动滚动、可选择复制；查看历史或选择文本时，新日志不会强制跳到末尾或清除选择。
- **V2.8 全新安装清理恢复**：含只读缓存文件的中断产品数据可在明确选择全新安装后清理；受管目录内的重解析点只删除链接本身、不访问其目标。无法删除时，安装器错误准确包含受管根目录与失败项。
- **V2.9 回滚关闭竞争**：点击“停止并回滚”后，在停止和回滚的每个可见阶段重复点击窗口关闭按钮；窗口不得退出，直到回滚完成并显示失败结果，且本次受管安装目录、缓存和注册项均已按回滚策略清理。

## 3. npx 与数据隔离

- **V3.1 命令约束**：客户端通过未锁版本的 `npx @deepseek-ai/dsh web` 供应和启动 DSH，不执行 `npm install` 或全局安装。
- **V3.2 缓存隔离**：npx 下载只写入安装清单记录的私有 npm cache，不写入或删除用户共享 npm cache。
- **V3.3 DSH_HOME 隔离**：DSH profiles、插件、设置、凭据和会话均落入客户端私有 `DSH_HOME`。
- **V3.4 启动目录**：DSH 从客户端空白启动目录运行，不把安装目录或安装器当前目录作为默认用户工作区。
- **V3.5 版本变化**：缓存清理或 registry 版本变化后，客户端仍按相同未锁版本命令启动，不显示可用版本、版本比较结果或升级提示 UI。
- **V3.6 供应活动**：启动时显示“正在检查 DSH 更新”；仅在 npx 的可识别输出表明下载、解压或安装时显示“正在更新 DSH”，不显示伪造的下载百分比或版本比较结果。
- **V3.7 供应错误**：模拟 npx 的网络错误和包安装错误时，分别显示“检查 DSH 更新时网络错误”和“更新 DSH 失败”；原始 stderr 仅记录到运行日志。

## 4. DSH 生命周期

- **V4.1 就绪判定**：仅有监听端口但返回非 DSH 内容时不得判定成功；DSH 页面身份验证通过后才显示 WebView。
- **V4.2 端口冲突**：3080 或持久化端口被未知进程占用时选择新端口，不接管、不终止未知进程。
- **V4.3 精确停止**：托盘退出只终止客户端拥有的 npx/Node/DSH 进程树，其他 Node 进程持续运行。
- **V4.4 优雅退出**：正常退出先触发 DSH 清理并等待限定时间；超时后只强制停止受管进程组。
- **V4.5 异常退出**：DSH 崩溃后客户端显示故障和日志入口，不发生无限快速重启。
- **V4.6 单实例**：重复启动不创建第二个 DSH，既有实例的主窗口被激活。
- **V4.7 只读诊断**：安装器、故障页面和 `--doctor` 对同一环境给出一致结果，诊断默认不修改系统或产品数据。
- **V4.8 有限修复**：启动失败最多普通重试一次；仅在确认私有缓存异常后清理私有 npx cache 并再试一次，不删除 `DSH_HOME`。
- **V4.9 错误状态**：启动失败与 DSH 就绪后的异常退出使用不同状态标题；前台窗口和后台托盘对同一故障显示相同类别。

## 5. 窗口、WebView 与托盘

- **V5.1 标准窗口**：主窗口使用操作系统原生标题栏、拖动、最小化、最大化和关闭行为，不绘制自定义标题栏。
- **V5.2 WebView 范围**：安装和启动阶段不创建 WebView；DSH 就绪后直接呈现其 Web UI。
- **V5.3 无导航改写**：客户端不取消、重定向或转交 WebView 导航，也不注入宿主脚本桥接。
- **V5.4 业务交互**：内嵌 DSH Web UI 能完成工作区选择、普通输入和一轮流式响应。
- **V5.5 数据隔离**：Windows WebView2 使用客户端私有用户数据目录；macOS WKWebView 使用产品独立数据存储。
- **V5.6 Avalonia 托盘**：托盘由 Avalonia `TrayIcon` 创建；Windows 和 macOS 均可从菜单打开主窗口并退出。
- **V5.7 关闭行为**：安装完成后关闭主窗口仅隐藏窗口，DSH 与托盘继续运行；安装过程中关闭会进入停止与回滚确认。
- **V5.8 启动状态一致性**：前台主窗口显示 DSH 检查/更新/启动阶段；后台登录启动保持窗口隐藏，并在托盘提示文本显示相同阶段、就绪或故障状态。

## 6. 自启动

- **V6.1 默认注册**：全新成功安装后，操作系统登录项中出现本产品，命令使用后台启动参数。
- **V6.2 后台体验**：登录启动时客户端和 DSH 正常运行，托盘可用，主窗口不主动弹出。
- **V6.3 尊重系统设置**：用户在操作系统中禁用后，普通启动和覆盖安装不会擅自重新启用。
- **V6.4 卸载注销**：卸载后本产品登录项消失，其他登录项不变。

## 7. 干净卸载

- **V7.1 运行中卸载**：卸载器能够协调正在运行的客户端，先销毁 WebView、停止 DSH，再删除文件。
- **V7.2 精确删除**：客户端安装目录、状态、日志、私有 npm cache、`DSH_HOME`、启动目录和 WebView 数据全部删除。
- **V7.3 工作区保留**：多个外部工作区及其中由 DSH 创建或修改的文件均保持不变。
- **V7.4 系统环境保留**：系统 Node.js、用户 npm 配置、共享 npm cache 和其他 Node 进程保持不变。
- **V7.5 无锁残留**：Windows WebView2 和应用文件无锁定残留。macOS 不属于项目验证目标。
- **V7.6 幂等恢复**：卸载中断后再次运行卸载器可继续清理，不扩大删除范围。
- **V7.7 运行中卸载握手**：运行中的客户端收到卸载 IPC 后先销毁 WebView 并停止其受管 DSH；卸载助手在实例互斥体释放前不得开始删除。无法建立握手或等待超时时保留文件并报告失败。

## 8. 平台发布

- **V8.1 Windows AOT**：本机 `win-x64` Native AOT 发布成功；真实产物完成启动、安装事务、托盘、WebView 和卸载验证。
- **V8.2 macOS 兼容性范围**：macOS 不属于项目发布或验收目标；外部开发者可自行从源码构建和验证，不要求产出、签名、公证或上传任何 macOS 包。
- **V8.3 AOT 无 .NET 前置**：在未安装 .NET Runtime 的测试系统上，AOT 安装器、客户端和卸载器均正常运行。
- **V8.4 .NET 依赖安装**：.NET 依赖包在已安装匹配 .NET Desktop Runtime 的系统上完成与 AOT 产物相同的核心安装和运行测试；缺少运行时时，AOT SetupHost 在启动 Avalonia 客户端负载前显示明确的原生前置条件错误，并且不创建产品安装目录或注册项。
- **V8.5 源码构建**：安装 .NET SDK 后可执行普通构建、`dotnet run -- --development` 和测试，且不要求 Native AOT 才能进入开发循环。
- **V8.6 非便携准入**：正式验收以平台安装器为入口；直接运行开发构建不代表安装与卸载验收通过。
- **V8.7 GitHub Release**：只发布 Windows `win-x64` 产物到 GitHub Releases，版本文件不可变，并同时提供 SHA-256、前置条件和签名状态。未签名 Windows 社区预览必须展示 SmartScreen 风险、校验步骤和不导入根证书的说明。
- **V8.8 无商店渠道**：项目不生成 Microsoft Store、WinGet 或客户端更新渠道所需的包、清单和运行逻辑。
- **V8.9 Windows SetupHost 输出**：在 Windows 本机构建 `-Version vX.Y.Z` 时，Native AOT SetupHost 分别内嵌 AOT 与 .NET 依赖客户端负载，生成 `artifacts/installer/DSH-Desktop-Setup-vX.Y.Z-win-x64-aot.exe`、`DSH-Desktop-Setup-vX.Y.Z-win-x64-dotnet.exe` 及各自 SHA-256 文件。每个下载物只有一个 EXE，不包含 PDB；有可用证书时在最终封装后完成 Authenticode 签名，无证书时只能按未签名 Windows 社区预览规则发布。
- **V8.10 Windows 单界面与宿主生命周期**：运行 SetupHost 后不出现终端窗口或第二套安装向导，只显示中文 Avalonia 安装引导。并发运行使用独立 staging；构造路径穿越、绝对路径、符号链接、重解析点、长度或 SHA-256 不匹配的负载时，SetupHost 在启动客户端前拒绝安装。正常、失败和停止场景均在 Avalonia 子进程退出前保留完整负载，退出后清理 staging；成功时清理完成后才启动受管安装目录中的客户端。
- **V8.11 显式安装角色**：直接运行开发或发布目录中的 `DshNgDesktop.exe` 不会隐式执行安装事务；只有 SetupHost 提供的显式安装会话参数可进入安装引导。安装成功后系统应用列表的卸载入口指向受管安装目录，不依赖原始下载文件或临时 staging。
- **V8.12 独立发行与源码洁净**：桌面 Release 使用 `desktop-vX.Y.Z` 标签；`artifacts/installer/`、安装器、校验值和签名副产物均不被 Git 跟踪，并可与其他子项目的 Release 并存。

## 9. 测试策略

- 本地专属测试工程固定为 `dsh-ng-desktop/LocalTests/`，并由根目录 `.gitignore` 精确排除；主项目必须从编译项中排除该目录，不得将其加入 Git 索引、解决方案、CI 输入或正式发行物。
- 本地测试工程可引用 `DshNgDesktop.csproj`，但测试临时文件必须位于测试工程的输出目录或显式的测试专属产品根目录；每项测试负责清理自己创建的数据。
- 纯状态机、路径所有权、端口选择、日志脱敏和补偿操作必须有自动化单元测试。
- npx 进程、HTTP 健康检查和失败回滚使用可控替身完成自动化集成测试。
- DSH 供应与监督至少覆盖：Node/npx 缺失或版本命令失败、私有环境变量与安全工作目录、持久化端口复用与冲突迁移、非 DSH HTTP 响应拒绝、进程所有权绑定、优雅/超时停止，以及普通重试和私有 cache 修复重试的次数上限。
- 安装器、托盘、自启动、WebView、系统退出和卸载必须在真实 Windows `win-x64` 环境进行人在环验收；macOS 验证不属于项目门禁。
- CI 如启用，只在 Windows 对 `win-x64` 执行 Native AOT 发布；普通 `dotnet build` 成功不能代替该门禁。
- `Avalonia.Controls.WebView` 及每个新增第三方依赖都必须由真实 AOT 产物验证，不得仅凭包声明判定兼容。
- SetupHost 的自动化测试必须覆盖负载清单校验、路径穿越与重解析点拒绝、缺文件或哈希损坏、子进程退出码传递、并发 staging 隔离和成功/失败后的临时目录清理；真实 Windows 验收额外确认整个进程期间无控制台窗口闪现。
- 破坏性测试只能操作测试专属产品目录和测试工作区，禁止以共享 Node/npm 数据作为清理目标。
